    7. 人工打分两条路径

    7.1 Annotation Queue vs User Feedback

    Langfuse 把"人工评分"分成两条独立路径——很多人误把它们合并，实际是两种角色 + 两种入口 + 两种数据流：

    维度Annotation QueueUser Feedback
    角色 内部标注者：PM / 领域专家 / 标注员 终端用户：app 的实际使用者
    入口 Langfuse UI 的 Annotation Queue 页面 产品内嵌的 👍 / 👎 按钮 / Browser SDK / REST API
    数据流 Admin 主动 curate 一批数据让人评（queue + 处理） Runtime 被动收集（用户点击）
    典型场景 难样本精标 / LLM Judge 不确定的 case / 校准 baseline 线上 app 的 👍👎 / 5 星评分 / 反馈文本
    量级 百到千级 / 周期 日均万到百万级
    延迟 小时到天（人工处理） 毫秒级（API 上报）
    直觉：Annotation Queue = "我把数据放进盒子里让人来打分"；User Feedback = "用户在我的产品里点了个按钮"。两种人工，但工作流和数据流完全不同。

    7.2 Annotation Queue 工作流

    New Queue 按钮 → 选 Score Configs（决定要打的分有哪些）→ 命名 2. Trace 列表 checkbox + Actions → Add to queue（可批量） 3. 在队列设置里指定 assignee user（多人并行处理不同 trace）

    7.3 创建队列 + 批量入队 + 处理（最简步骤）

    UI 入口都在顶栏 Annotations 标签页：

    1. 创建队列：New Queue → 选 Score Configs（预先建好的评分模板）→ 命名 → 描述 → 可选分配 user
    2. 添加 trace：从 Tracing 列表勾选若干 trace → Actions → Add to queue
    3. 处理：进入队列页 → 点 trace → 在右侧 Annotate 卡上打 Score Configs 列出的所有分 → Complete + next 推进下一条
    4. 查询结果：队列的 Score Configs 名下的 score 全部进入 dashboard，可按 queue 过滤
    ⚠️ 关键：Score Configs 必须先在 UI 建好（lesson 0005-01 §2.3），queue 创建时选它——queue 处理时打分用的就是这个 config 的 data_type + categories。

    7.4 User Feedback 闭环

    和 score 组合（score.user-feedback=1 看所有 👍 用户） • 可关联 prompt version：回到这条 trace → Prompt 徽章 → 看哪版 prompt 收获 👍 多

    7.5 Browser SDK 实战（web 端 👍👎）

    Browser SDK 是 Langfuse 给前端的官方 SDK——只在浏览器里跑，不依赖后端转发：

    // 浏览器端（TypeScript / React / Vue 都可）
import { LangfuseBrowserClient } from "@langfuse/browser";

// 1. 初始化（用 Public Key，仅前端可读）
const lf = new LangfuseBrowserClient({
  publicKey: process.env.NEXT_PUBLIC_LANGFUSE_PUBLIC_KEY!,
  baseUrl: window.location.origin,   // 或 langfuse 域名
});

// 2. 用户点 👍 时上报
async function onThumbsUp(traceId: string) {
  await lf.score({
    traceId: traceId,
    name: "user-feedback",
    value: 1,                          // BOOLEAN：1=👍, 0=👎
    dataType: "BOOLEAN",
    comment: "thumbs up via web UI",
  });
}

// 3. traceId 从后端响应里取
// 假设后端在 chat 响应里返回 { trace_id: "01H...", answer: "..." }
// 前端存到 sessionStorage：sessionStorage.setItem("last_trace_id", traceId)
// 点击 👍 时：onThumbsUp(sessionStorage.getItem("last_trace_id"))
    为什么需要后端回传 traceId？ Browser SDK 默认不会自动拿到当前请求的 traceId（那是后端 SDK 产生的）。最简模式：后端在 chat 响应里加一个 trace_id 字段，前端在响应后存起来。

    7.6 REST API 集成（web 后端 / 移动端）

    更灵活的选择：后端代前端发请求，统一控制权限 / 限流：

    import requests

def record_user_feedback(
    trace_id: str,
    public_key: str,
    secret_key: str,
    langfuse_host: str,
    thumbs_up: bool,
    comment: str = "",
):
    """后端转发用户反馈到 Langfuse。可加限流、审计日志等。"""
    response = requests.post(
        f"{langfuse_host}/api/public/scores",
        auth=(public_key, secret_key),       # ← 用 Secret Key 鉴权
        headers={"Content-Type": "application/json"},
        json={
            "traceId": trace_id,
            "name": "user-feedback",
            "value": 1 if thumbs_up else 0,
            "dataType": "BOOLEAN",
            "comment": comment or ("thumbs up" if thumbs_up else "thumbs down"),
        },
        timeout=5,
    )
    response.raise_for_status()
    return response.json()

    逐行说明：

    • auth=(pk, sk)：HTTP Basic Auth，Secret Key 必须在服务端用，绝不外泄
    • traceId：camelCase 是 REST API 约定；SDK 里是 trace_id 蛇形命名
    • dataType：camelCase 同理
    • timeout=5：用户反馈链路不能阻塞主流程；失败时静默记日志即可

    7.7 ⚠️ Anti-pattern：把 user feedback 当 ground truth

    Anti-pattern：用 👍👎 直接当评测指标，prompt 优化只追求 👍 多。

    为什么是坑：
    • 采样偏差——主动点 👍 的往往是开心 / 满意用户；沉默 / 不满用户不会反馈
    • 操纵风险——如果用户知道 👍 会让模型更"奉承"，prompt 会偏向讨好而非有用
    • 对长 query 不友好——复杂任务用户懒得评，得到的都是简单 case 的 👍
    修复：把 user feedback 当辅助信号，主评测仍是 LLM-as-a-Judge + Code Evaluator + Annotation Queue。User feedback 用来发现"用户感知到的失败"——例如 👎 多 + LLM Judge 分数高 = judge 漏判的痛点，专门投到 Annotation Queue 让专家精标。
    🎯 动手任务 §7（20 分钟）
    1. 打开 Langfuse UI → Annotations → → 选 5 条 lesson 0005-02 的 judge-helpfulness score 低的 trace → 加到新 queue "low-quality-review"

    3. UI 给每条 trace 打 quality 分 → 在 Scores tab 确认出现
    4. 运行 src/apps/fuse/user_feedback_demo.py → 它会 POST 一条 user-feedback score 给之前 scoring_demo 留下的那条 trace

    8. UI 查 Score + Score Analytics

    8.1 Trace 详情页的 Scores tab

    打开任一 trace，右上角的 Scores 标签页会列出挂在该 trace + 所有 observation 上的 score：

    8.2 按 score 过滤

    Langfuse 顶部搜索栏支持组合过滤：

    # 单 score
score.user-feedback=1                  # 所有 👍
score.judge-helpfulness < 0.5          # 所有 judge 判低的

# 多 score
score.user-feedback=1 AND score.judge-helpfulness > 0.8   # 双方都赞

# 与 metadata 组合
metadata.environment=prod AND score.helpfulness > 0.7     # prod + 质量高

# 与 tag 组合
tag:experiment-A AND score.helpfulness < 0.5              # 实验 A 组里差评的

    这是个超强的反向工程工具：发现一个回归 → 按 metadata 切片定位哪个 prompt / 哪个 user tier 出错。

    8.3 Score Analytics 仪表板

    顶部 Scores → Analytics 标签进入。4 个区域：

    8.4 双 score 比较：何时用哪种指标

    指标何时用含义
    Pearson 两个 NUMERIC score 是否线性相关 -1 到 1；越接近 1 越相关
    Spearman 同上但基于 rank（抗 outlier） 适合分布奇怪的数据
    MAE / RMSE 两个 NUMERIC score 的偏差有多大 0 起，越大偏差越大
    Cohen's Kappa 两个 CATEGORICAL / BOOLEAN 评分者的一致性 扣掉随机一致后的真正一致率
    F1 两个 BOOLEAN score 的精确率 / 召回率 适合"找出 X"的场景

    典型实战：判断 "user-feedback 和 LLM Judge 是否一致"——用 Cohen's Kappa。如果 Kappa < 0.4，说明 judge 没学懂用户偏好，需要校准。

    8.5 ⚠️ Matched vs All tab 的语义

    双 score 分析有两个 tab，含义不同：

    Tab显示什么何时用
    Matched 只显示两个 score 都挂在同一 parent的样本 有效比较（A 的 trace 上有 A1 和 A2 两个 score）
    All 分别显示每个 score 的完整分布（不要求共现） 看覆盖率（A1 score 多但 A2 score 少 → A2 覆盖不全）
    ⚠️ 误读：把 All 当 Matched 用——会高估一致性（两者分布不一样大的情况下，All 的 Kappa 会偏低但 Matched 才是真实一致性）。

    8.6 Dashboard 趋势实战：发现回归

    把刚才学的拼起来，发版后 5 分钟内定位回归：

    1. 看 score 趋势图：Analytics → score helpfulness → Trend Over Time → interval=5m → 看发版时间点（git sha 切换的 timestamp）
    2. 下降定位：如果 mean 从 0.8 掉到 0.6 → 点那个时间点 → 看命中哪些 trace
    3. 切片分析：用 metadata 组合：release=<new-sha> AND score.helpfulness < 0.5 → 看具体 trace
    4. 点开 trace：看 Prompt 徽章 → 确认是新版 prompt → 对比旧版 → 找差异

    9.1 score 不出现在 UI 上（5 个 root cause 决策树）

    新人最常见的问题。决策树逐项排除：

    9.2 - 9.7 其他 6 类坑

    #症状根因修法
    9.2 同 name 的多次 score 调用后只有最后一条 score_id（如不指定 Langfuse 不去重，但 UI 显示顺序可能乱）+ 时机 不指定 score_id 让每次都是新 score；只关心最新值时再考虑覆盖
    9.3 judge 输出格式不稳 prompt 没强约束 / temperature 高 三 trick：低 temp + JSON 强约束 + response_format（详见 Part 2 §6.4）
    9.4 score 关联到错对象 4 个 parent 字段填错 用 Part 2 §4.3 决策树
    9.5 LLM judge 烧钱 sampling rate=1.0 + rule 匹配范围太宽 sampling 0.05-0.1 + filter isRootObservation=true
    9.6 CATEGORICAL 400 value 不在 config 预定义里 UI Score Configs 加对应 category
    9.7 v4 trace-level evaluator 弃用 旧项目挂错层级 改 observation-level + isRootObservation=true filter

    9.8 自检清单（每个 score 写完跑一遍）

    # Score 写入前的 6 项 checklist：
# 1. name 已在 UI Score Configs 建好？
# 2. CATEGORICAL 的 value 在 categories 里？
# 3. 4 个 parent 字段组合正确（挂 observation 必须给 trace_id + observation_id）？
# 4. 在 observation context 内？（用 score_current_*）或显式传 trace_id（用 create_score）？
# 5. flush() 在 score 调用之后？
# 6. 已绑定的 prompt（如有）传的是 PromptClient 对象不是字符串？
