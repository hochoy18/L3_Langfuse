    三种 Evaluator 实现：SDK / Code / LLM-as-a-Judge

    预计 60 分钟 · 难度 ★★★★☆ · 涵盖 §4-6；Part 1 已讲 Score 4×4 矩阵与 Evaluator 一等公民概念，本节落地 3 种实现方式
    本节 3 个目标
    1. 掌握两种 SDK 打分风格（上下文内 vs 低层 API）的取舍，能写内联 Evaluator 函数
    2. 能写 Code Evaluator（3 个常见规则 + 单测），理解其严格约束
    3. 能设计 LLM-as-a-Judge（prompt 三段式 + 解析 fallback），避开常见 anti-patterns

    4. 手工 SDK 打分

    4.1 两种风格：上下文内 vs 低层 API

    Langfuse SDK 给你两种调用风格，对应你"在不在 observation 上下文里"的两种场景：

    经验法则：在 agent / ReAct 代码里用上下文内（自动找到 trace_id）；在 web 后端 / 异步 worker 用低层（手动传 trace_id）

    4.2 上下文内打分：score_current_trace 与 score_current_span

    在 @observe 装饰的函数里（或 start_as_current_observation 块内），当前活跃的 trace / span 自动可用——直接调 score_current_* 即可，不用手填 trace_id。

    from langfuse import observe, get_client

@observe()
def handle_user_question(question: str) -> str:
    lf = get_client()

    # 跑 LLM 拿答案
    answer = call_llm(question)

    # 直接给当前 trace 打分（自动绑定到当前 trace）
    lf.score_current_trace(
        name="user-feedback-prompt",
        value=1,                   # BOOLEAN 类型，必须 0 或 1
        data_type="BOOLEAN",
        comment="auto: response generated successfully",
    )
    lf.score_current_trace(
        name="response_length",
        value=len(answer),          # NUMERIC 类型
        data_type="NUMERIC",
    )

    return answer

    逐行说明：

    • score_current_trace(...)：在 observation 上下文内自动找到 trace_id，无需手填
    • name：必须先在 UI Score Configs 里建过——否则 CATEGORICAL 会被服务端 400 拒绝
    • value：必须按 data_type 走——BOOLEAN 必须是 0/1，NUMERIC 是 float
    • comment：评分理由（≤ 500 字符）；LLM Judge 场景几乎必填
    • 同一 trace 可以打多个 score：score_current_trace 调多次不覆盖

    如果想打给具体某个 observation（不是 trace），用 score_current_span：

    @observe()
def handle_request(question: str):
    lf = get_client()

    # 进入一个嵌套 span
    with lf.start_as_current_observation(as_type="span", name="preprocess") as span:
        cleaned = preprocess(question)

        # 打给这个 span（不是父 trace）
        lf.score_current_span(
            name="preprocess-cleaned-ratio",
            value=len(cleaned) / len(question),
            data_type="NUMERIC",
        )

    4.3 低层 API：create_score 的 4 个 parent 字段

    不在 observation 上下文里（异步 worker / web 后端 / 跨 trace 评分）→ 用低层 API。score 必须挂在某个 parent 上，4 选 1+：

    parent何时用SDK 参数
    trace_id 最常见；评价整次调用 create_score(trace_id="01H...")
    observation_id 评价某个具体 step（必须同时给 trace_id） create_score(trace_id=..., observation_id=...)
    session_id 评价整个多轮会话（不与 trace 关联） create_score(session_id="sess-...")
    dataset_run_id 离线实验场景（0006 详讲） experiment runner 自动填 
    from langfuse import get_client

lf = get_client()

# 例 1：异步 worker 收到 trace_id 后打分
async def score_worker(trace_id: str, output: str):
    lf.create_score(
        name="length-check",
        value=len(output),
        data_type="NUMERIC",
        trace_id=trace_id,
        comment="scored async 2 minutes after response",
    )

# 例 2：跨多 trace 汇总，挂到 session 级
def score_session(session_id: str, all_outputs: list):
    avg_quality = sum(quality(o) for o in all_outputs) / len(all_outputs)
    lf.create_score(
        name="session-overall-quality",
        value=avg_quality,
        data_type="NUMERIC",
        session_id=session_id,        # ← 不传 trace_id，挂整个 session
    )
    ⚠️ 坑：同时填 trace_id + session_id 会被服务端忽略其余字段（参见 §4.3 决策树）。挂 observation 必须同时给 trace_id + observation_id，单独给 observation_id 会 400 拒绝。

    4.4 Session 级评分实战模式

    Session 级 score 最常见的场景是多轮对话结束后的总评——单独看每轮 trace 没意义，要看整段对话体验：

    @observe()
def end_conversation(session_id: str, messages: list):
    """用户在 web 端点关掉聊天窗口时调用。"""
    lf = get_client()

    # 整段对话的体感指标
    avg_latency = compute_avg_latency(messages)
    user_satisfaction = infer_satisfaction(messages)

    # 关键：传 session_id 而非 trace_id
    lf.create_score(
        name="session-satisfaction",
        value=user_satisfaction,
        data_type="NUMERIC",
        session_id=session_id,
        comment=f"computed over {len(messages)} turns",
    )

    UI 上 Sessions 标签页能聚合这些 score：按 session 看整体满意度，比单条 trace 看体验更准。

    4.5 挂到具体 generation：observation.score_trace()

    有时候你不光想给整条 trace 打分，还想给特定那个 generation 节点打——比如 agent 多步决策里第二步第二部明显走偏。可以用 observation.score_trace() 把 score 挂到具体节点：

    @observe(as_type="generation", name="ask_critic")
def ask_critic(question: str) -> str:
    lf = get_client()

    # 这一步 generation 的内部质量分
    answer = call_llm(question)

    lf.update_current_generation(
        prompt=prompt_obj,
        usage_details={"input": 50, "output": 30, "total": 80},
    )

    # 给这个 observation 打分（不是给父 trace）
    lf.score_current_span(
        name="generation-specific-helpfulness",
        value=0.85,
        data_type="NUMERIC",
    )
    return answer

    注意：在 @observe(as_type="generation") 内部，score_current_span 实际是给当前 generation（它也是一种 observation）打分，不是给父 trace。

    4.6 内联 Evaluator 函数模式

    前面 4.1-4.5 都是调用方主动给 trace 打分。但更工程化的做法是：把打分逻辑抽成一个evaluator 函数——业务代码只调一次 evaluate(output)，函数内部决定用什么方式打分。这就是后面 §5 / §6 要展开的 evaluator 模式。最小骨架：

    def rule_output_present(output: str) -> tuple[float, str]:
    """最简规则型 evaluator。返回 (value, comment)。"""
    if not output or not output.strip():
        return 0.0, "empty output"
    return 1.0, "non-empty output"


@observe()
def handle(question: str) -> str:
    lf = get_client()
    answer = call_llm(question)

    # 调 evaluator 函数
    value, comment = rule_output_present(answer)

    # 把结果写回 trace
    lf.score_current_trace(
        name="output-present",
        value=value,
        data_type="NUMERIC",
        comment=comment,
    )
    return answer

    后面 §5 / §6 我们把这个模式升级：规则型用 Python 函数 + UI 注册，LLM Judge 用另一个 LLM 调用 + JSON 解析，但接口形态都和上面这个一致（返回 score 数据）。这就是 Langfuse evaluator 的设计哲学——实现方式多种，接口形态统一。

    5. 规则型 / Code Evaluator

    5.1 何时用 rule vs LLM judge

    Code Evaluator 适用的场景有非常清晰的边界——LLM Judge 适合 rule 答不了的"主观"判断。把决策做成表：

    检查类型典型例子推荐方式
    确定性 / 客观 JSON 是否合法、长度限制、关键词包含、邮件格式、整数范围 ✅ Code Evaluator
    exact match 实验里 output == expected_output ✅ Code Evaluator
    工具调用检查 调了正确的 tool、参数 schema 对得上 ✅ Code Evaluator
    语义 / 主观 helpful / tone / 是否礼貌 / 是否有歧义 ❌ → LLM Judge
    事实正确性 "法国的首都是巴黎" 是否真 ❌ → LLM Judge（rule 查不了真值）

    5.2 严格代码约束（注册到 UI 时）

    ⚠️ 关键约束（如果走 UI 注册路径）：
    • 仅标准库——不能用 numpy / requests / 任何第三方包
    • 2 秒超时——超时的 evaluator 会被强制 kill，整条 score 丢失
    • 源码 < 256 KB
    • 签名必须是 def evaluate(ctx) -> EvaluationResult（不是 class）
    • ctx.experiment 在 observation-only 评估时为 None——代码必须兼容
    想用 requests 调外部 API？→ 走 LLM-as-a-Judge，让 LLM 替你调，或在业务代码里先调完把结果放 metadata。

    5.3 签名 + 最小模板

    from langfuse import EvaluationContext, EvaluationResult, Score

def evaluate(ctx: EvaluationContext) -> EvaluationResult:
    """Code Evaluator 的唯一签名。
    """
    ctx    # EvaluationContext，包含当前 observation / experiment 上下文
    output = ctx.observation.output  # 触发本次评估的 observation 输出

    # 返回的每个 Score 都会作为一条 score 写回
    return EvaluationResult(scores=[
        Score(
            name="output_present",          # 已在 UI Score Configs 注册过
            value=output is not None,        # True / False
            data_type="BOOLEAN",
            comment="present" if output else "missing",
        ),
    ])

    5.4 三个常见规则（完整可复用）

    规则 1：output 是否存在（最简模板）

    def rule_output_present(ctx):
    """output 是否非 None 且非空字符串。"""
    output = ctx.observation.output
    present = bool(output and str(output).strip())
    return EvaluationResult(scores=[Score(
        name="output_present",
        value=int(present),                 # BOOLEAN: 0 或 1
        data_type="BOOLEAN",
        comment="present" if present else "missing or empty",
    )])

    规则 2：exact match（实验场景对比 expected）

    def rule_exact_match(ctx):
    """observation output vs experiment item expected_output。
    仅在 dataset experiment 里 evaluate(ctx) 会被传入 ctx.experiment；
    observation-only 评估时 ctx.experiment 是 None，score 直接返回 None。
    """
    expected = ctx.experiment.item_expected_output if ctx.experiment else None
    actual   = ctx.observation.output

    if expected is None:
        # observation-only 评估没有 expected，跳过
        return EvaluationResult(scores=[])

    return EvaluationResult(scores=[Score(
        name="exact_match",
        value=int(actual == expected),
        data_type="BOOLEAN",
        comment=f"expected={expected!r} actual={actual!r}",
    )])

    规则 3：长度 + 关键词检查（组合规则）

    def rule_length_and_keyword(ctx, min_chars: int = 20, required_keyword: str = "答案"):
    """检查 output 长度 & 是否含关键词，返回两个独立 score。"""
    output = str(ctx.observation.output or "")

    return EvaluationResult(scores=[
        Score(
            name="response_length",
            value=float(len(output)),
            data_type="NUMERIC",
            comment=f"len={len(output)}",
        ),
        Score(
            name="contains_required_keyword",
            value=int(required_keyword in output),
            data_type="BOOLEAN",
            comment=f"required={required_keyword!r}",
        ),
    ])

    6. LLM-as-a-Judge

    6.1 何时用 LLM Judge

    Code Evaluator 答不了"这个回答对用户有没有帮助"、"语气是不是礼貌"、"事实是不是真"——这些需要语言理解。把决策做成表：

    评估问题推荐方式
    "回答有没有切中用户问题"LLM Judge（语义匹配）
    "语气是否友好 / 礼貌"LLM Judge
    "事实是否正确"LLM Judge（除非有 ground truth 库）
    "是否包含有害内容"LLM Judge + Guardrail
    "是否调用了正确的 tool"Code Evaluator（确定性）
    "JSON 格式合法"Code Evaluator

    6.2 Judge prompt 三段式

    一个好的 judge prompt 必须有 3 段，缺一不可：

    You are evaluating an AI assistant's response for helpfulness.

        # 1. 评分维度 / 评分标准（rubric）
        Score on a 1-5 scale:
        - 5 = perfect, addresses the question completely and concisely
        - 4 = good, addresses with minor issues
        - 3 = acceptable, partially addresses
        - 2 = poor, misses key points
        - 1 = useless, off-topic or empty

        # 2. 待评估的输入 / 输出（实际变量）
        User question: {question}
        Assistant answer: {output}

        # 3. 输出格式约束（强制 JSON 便于解析）
        Output ONLY a JSON object, no preamble:
        {"score": <int 1-5>, "reason": "<one sentence>"}

    逐段说明：

    • 第 1 段（rubric）：评分标准必须明确 + 可执行。避免"好 / 不好"这种主观词；用"包含 X"、"长度在 N-Y 之间"、"引用了 Z 数据源"这种可判断的描述
    • 第 2 段（变量）：{question} 和 {output} 是占位符——由代码用真实值填充
    • 第 3 段（输出格式）：必须强制 JSON，否则解析 fallback 会很频繁（§6.4 详讲）
    经验法则：judge prompt 的 prompt 长度通常是用户 prompt 的 3-5 倍——你越想让 judge 评判得准，rubric 就越要写细。

    6.3 完整 LLM Judge 函数（带 JSON parse fallback）

    不要让 judge 看 metadata / tags（§6.7 anti-pattern） • 解析失败时 fallback 到 0.5（中性分）+ 写详细 comment，不要 silent fail • judge 用低 temperature（0-0.3）+ 输出格式约束 + 三段 prompt 模板

    完整 LLM Judge 函数实现（含 fallback）：

    import json
import re
from langfuse import get_client

JUDGE_PROMPT = """You are evaluating an AI assistant's response.
Score on 1-5 scale for helpfulness.
Output ONLY JSON: {"score": <int>, "reason": "<one sentence>"}

Question: {question}
Answer: {answer}
"""

def judge_helpfulness(question: str, answer: str, judge_llm) -> tuple[float, str]:
    """返回 (value, comment)。失败时 fallback 到 (0.5, parse_error)。"""
    try:
        resp = judge_llm.invoke(
            JUDGE_PROMPT.format(question=question, answer=answer),
            temperature=0,  # ← 关键：低 temperature 让 judge 稳定
        )
        # 解析 JSON（response_format 在支持的 provider 上更可靠）
        parsed = json.loads(resp.text)

        # 校验范围
        score = float(parsed["score"])
        if not (1.0 <= score <= 5.0):
            return 0.5, f"out-of-range score={score}, fallback"

        # normalize 到 0-1（Langfuse NUMERIC 习惯）
        normalized = (score - 1) / 4
        return normalized, parsed.get("reason", "")

    except (json.JSONDecodeError, KeyError) as e:
        # JSON 解析失败：从原文尝试 regex 抢救
        m = re.search(r'"score"\s*:\s*(\d+)', resp.text)
        if m:
            score = float(m.group(1))
            if 1.0 <= score <= 5.0:
                return (score - 1) / 4, f"recovered from regex: {resp.text[:80]}"
        return 0.5, f"parse_error: {e}; raw={resp.text[:100]}"


@observe()
def handle_with_judge(question: str) -> str:
    lf = get_client()
    answer = call_llm(question)        # 业务 LLM（可以不同 model）

    # 调 judge（独立 LLM 调用）
    value, comment = judge_helpfulness(
        question=question,
        answer=answer,
        judge_llm=judge_llm_client,    # 可以用 gpt-4o / Claude / 你的 MiniMax
    )

    lf.score_current_trace(
        name="helpfulness",
        value=value,
        data_type="NUMERIC",
        comment=comment,
    )
    return answer

    6.4 输出格式约束的 3 个 trick

    LLM 输出不稳定——30% 情况下你不严格约束就会拿到非 JSON。三个稳定 trick：

    >
    trick作用缺点
    低 temperature（0-0.3） 输出分布更窄，更稳定 失去一些"创造力"——但 judge 本来就不该创造
    prompt 强约束（"Output ONLY a JSON object, no preamble"） 90% 情况下拿到干净 JSON 少数模型还是会偷偷加 prose
    OpenAI 的 response_format={"type": "json_object"} 服务端强制 JSON 输出，最可靠 仅 OpenAI / 部分 provider 支持

    三个同时用最稳：低 temperature + 强 prompt + response_format（如果支持）。

    6.5 Judge prompt 用 Evaluator 自带版本管理（不是 Prompt Management）

    ⚠️ 常见误区："我把 judge prompt 也放到 Prompt Management 里管理"——不行。Judge prompt 不是给业务用的，是给 evaluator 用的，归 Evaluator 资源自己带版本（"Updating its definition creates a new version, and active rules automatically use the latest version"）。

    业务 prompt（movie-critic / chat-system 等）→ Prompt Management（lesson 0004）
    Judge prompt → Evaluator 资源（LLM-as-a-Judge evaluator 的 definition 字段）

    6.6 挂到 production trace（observation-level + isRootObservation）

    把 LLM Judge evaluator 部署到 UI 后，配置 Rule 用经典 filter：

    {
  "type": "boolean",
  "column": "isRootObservation",
  "operator": "=",
  "value": true
}

    为什么用 isRootObservation？

    • 每条 trace 只评一次（root 那次 LLM 调用），不重复评子 observation
    • 精准 target root 的 output——root 通常是用户问题的直接 LLM 回答
    • 成本可控：production 上 10% sampling × root-only = = 流量 1/10

    6.7 Judge 的 anti-patterns（4 条 ⚠️）

    Anti-pattern 1：让 judge 看自己的输出
    如果用同一模型、同一 prompt 让 judge 评自己的输出，会循环自我确认。修复：judge 用不同模型（业务 GPT-4o， judge 用 Claude / Gemini / 别的）。
    Anti-pattern 2：judge prompt 用高 temperature
    Temperature > 0.5 → judge 输出随机性大，同一份输入两次跑分能差 1 分，整个 score 不可信。
    修复：judge 用 0-0.3。
    Anti-pattern 3：让 judge 看 metadata / tags
    如果 metadata 含 expected_score=0.9 之类的元信息，judge 会被污染。
    修复：构造 judge prompt 时只传 input/output，不要传 metadata。
    Anti-pattern 4：judge prompt 又短又模糊
    "Score the answer from 1 to 5" → judge 不知道怎么评 → 输出不稳定。
    修复：必须按 §6.2 三段式，每段 3-5 行。

    6.8 v4 trace-level deprecation 警告

    ⚠️ v4 已弃用 trace-level evaluator（2026-11-16 强制切）。
    历史代码如果挂在 trace 上：迁移期内还能跑但有 warning；新项目一律 observation-level。
    Rule filter 用 isRootObservation=true（§6.6）是 v3+ 推荐标准。
    🎯 动手任务 §6（30 分钟）
    1. 复用 lesson 0004 的 movie-critic prompt + LLM 拿一份输出
    2. 写 judge_helpfulness(question, output) 函数（按 §6.3 模板），用 不同 model（业务 MiniMax-M3， judge 用 gpt-4o-mini 或 Claude）
    3. 跑 5 次同一份输入，看 judge 输出波动——如果 > 1 分波动，temperature 调到 0

    7. 一句话总结

    Code Evaluator 用 stdlib 函数做确定性检查，LLM Judge 用另一个 LLM 做语义判断，两种实现统一返回 EvaluationResult(scores=[...])。生产部署走 UI 注册 + Rule filter（isRootObservation=true）。
