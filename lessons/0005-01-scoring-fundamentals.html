    LESSON 0005 · EVALUATION · PART 1 of 3

    从观测到评分：概念、数据模型与 Evaluator 一等公民

    预计 35 分钟 · 难度 ★★★☆☆ · 涵盖 §1-3；Part 2 讲 Evaluator 三种实现，Part 3 讲 Annotation Queue 与用户反馈
    本节 3 个目标
    1. 区分 observability（看发生了什么）和 evaluation（看好不好）
    2. 掌握 Score 的 4 种 data_type 和 4 个附加层
    3. 理解 Langfuse v3+ 的 Evaluator + Rule 生产级模式，避开 v4 trace-level 弃用坑

    1. 为什么需要评分

    1.1 Observability ≠ Evaluation

    Lesson 0002-0004 解决了"线上发生了什么"——每一次 LLM 调用的输入、输出、token、延迟、调用树，全部进了 Langfuse。但这些只是观测，回答不了另一个问题：

    "上周发版后，回答到底有没有变差？"
    "GPT-4o 和 Gemini Pro 哪个更贴合我们的语气？"
    "用户点 👍 的回答，是不是真的比点 👎 的好？"

    这些都是 evaluation 的范畴。两个概念的关系：

    关键关系：评估的对象不是凭空打分——它必须依附在某个 trace / observation 上。没有观测数据，评估无从谈起。

    1.2 三个典型场景

    场景没评估时怎么搞有评估时怎么搞
    发版后回归检测 用户反馈"变差了"才反应过来，已经过了几小时 每条 trace 自动打分，UI 看 score 趋势图，发版后 5 分钟内看到拐点
    Prompt A/B 决策 PM 拍脑袋决定、或者看 token 数量判断 两个 prompt 各跑 1000 条 trace，比 score 均值 + 标准差
    用户反馈闭环 👍👎 数据躺在数据库里，没人能关联到具体的 prompt 版本 每次 👍 直接变成一条 score 挂在 trace 上，能点回 prompt v3 看到底是哪版出错
    直觉：trace 是电影的"拍摄素材"（每一个镜头都在），score 是"评分"（这一镜到底演得好不好）。两者放在一起才有完整的 QA 闭环。

    1.3 三个常见误解 FAQ

    在动手写 score 之前，先澄清 3 个最常见的误解——它们是新人踩坑的高发区，每个都能让你浪费半天排查：

    误解 1：接 Langfuse 会拖慢我的 LLM 调用？
    真相：不会。SDK 内部是异步队列 + 批量 flush——app 调完 LLM 立即返回用户响应，trace 在后台批量上报。实测 latency 影响在毫秒级以内，可忽略。详见 §1.4 时序图。
    误解 2：trace 名字想怎么塞就怎么塞？
    真相：不行。 名字是 API——换名 = 所有 evaluator / dashboard / saved view 的引用静默失效，且不会报错。
    规则：动词开头（classify-intent / ask-llm / retrieve-context）、稳定 + 低基数 + 不含动态值（order-8945 ❌）+ 不含模型名（gpt-4o-ask ❌——模型名应放 generation.model 字段）。
    误解 3：把整个 agent 循环塞一个 trace 完事？
    真相：别。 一个 trace 内应让每个 LLM 调用成为独立 generation，每个 tool 调用成为独立 tool，彼此按调用顺序嵌套。 否则你看不清中间哪一步出了问题——token 滥用 / 工具失败 / 决策漂移都查不出来。 LangGraph / LangChain CallbackHandler 默认就生成这种结构，不要自己包成单一 observation。

    1.4 底层协议与运行机制

    Langfuse v3+ 底层基于 OpenTelemetry 开源标准——这意味着你的 trace 不仅能进 Langfuse，还能同时发给 Datadog / Jaeger 等多个后端（多 OTEL exporter 不会冲突）。

    下面这张时序图展示了一次 LLM 调用产生 trace、再上报到 Langfuse 的全过程：

    关键点（这张图背后的 4 条机制）：

    • 非阻塞——app 调完 LLM 立即返回，trace 在后台批量上报（实测 latency 影响 < 1ms）
    • 短脚本必加 flush()——一次性脚本在退出前必须显式调用，否则队列里未发送的 trace 丢失（Lesson 0002 hello_trace.py 已演示）
    • 长跑应用不需 flush——exporter 在独立线程持续运行，进程优雅退出时由 OTel SDK 处理
    • v4 默认 events_only——意味着传统 /api/public/traces REST 端点会 404；查数据请用 v2/observations API 或 npx @langfuse/cli

    2. Score 数据模型

    2.1 4 种 data_type

    Score 的 value 字段有 4 种合法类型，必须显式声明（否则 Langfuse 会按 value 推断，但推断结果不可控）：

    data_typevalue 取值典型场景
    NUMERIC float（建议 0-1 或 1-5） helpfulness 0.92、tone 0.7、latency penalty -0.3
    CATEGORICAL 字符串，必须匹配 config 中预定义的类别 "good" / "neutral" / "bad"；"correct" / "partial" / "wrong"
    BOOLEAN 数字 0 或 1（v3 API 读出时是 bool） pass / fail、含关键词 / 不含、JSON 可解析 / 不可解析
    TEXT 非空字符串，1-500 字符 judge 的 reasoning（一句话解释为何打这个分）
    ⚠️ 坑：CATEGORICAL 的 value 必须在 config 里预先定义；不写 config 直接发 "good" 会被服务端拒绝（HTTP 400）。生产做法是先在 UI 的 Score Configs 里建好类别，代码里只引用。

    2.2 Score 可附加在 4 层

    这是 Lesson 0005 最容易记错的地方——Score 不是只能挂在 trace 上，它有 4 个合法的 parent：

    为什么有 4 层？每个粒度对应一种问题：

    parent适用问题SDK 参数
    Trace 这一整次调用答得好不好？（最常用） score_current_trace(...) 或 create_score(trace_id=...)
    Observation 这一步 LLM 调用答得好不好？比如 agent 多步里的第二步是不是瞎说 span.score(...) 或 create_score(observation_id=...)
    Session 用户这一整轮对话结束体验如何？ create_score(session_id=...)
    Dataset Run 离线 experiment 里那条样本的整体评分（0006 详讲） experiment runner 自动挂，不手写
    经验法则：先想清楚你要回答"哪一层的问题"。如果不确定，从 trace 级 开始——99% 的评估挂 trace 就够了。

    2.3 Score Configs（必填的元数据）

    生产部署里，每个 score name 必须先在 UI 上"声明"——叫什么名字、什么 data_type、取值范围是什么、谁负责维护。这就是 Score Config。

    为什么有这个"配置"环节？三个原因：

    1. 校验输入：CATEGORICAL 的 value 必须是 config 里预定义的；NUMERIC 必须在 config 设的 min/max 之间
    2. Dashboard 渲染：UI 看到 config 就知道这列怎么画（图柱状图 vs 折线图 vs 分类卡）
    3. 权限与所有权：config 里指定 owner team，谁来维护这个分；不同团队分独立编号空间

    最小做法：

    # 一次性：在 UI 的 Score Configs 页面建好
#   name: helpfulness, data_type: NUMERIC, min: 0, max: 1
#   name: tone,        data_type: CATEGORICAL, categories: ["good","neutral","bad"]
#   name: user-feedback, data_type: BOOLEAN

# 之后代码里只用名字引用
lf.score_current_trace(name="helpfulness", value=0.85, data_type="NUMERIC")

    2.4 Score vs Metadata 边界

    这是新人最常混的概念。两者都是附加信息，但用途完全不同：

    维度MetadataScore
    目的 描述这次调用的上下文（哪个环境、哪个 user、哪个 feature flag） 评价这次调用的质量（这条输出好不好、是不是正确）
    数据形态 任意 dict，键值对 单值（+ 可选 comment + 可选 metadata）
    何时写 trace 创建时或过程中 trace 完成后，由 evaluator 或人写入
    UI 上 折叠的 "Metadata" 面板 独立的 "Scores" tab，可过滤、可聚合
    典型例 environment=prod, user_id=u-9f3a, prompt_version=3 helpfulness=0.85, tone="good", user-feedback=1
    一句话记法：Metadata 是"这条 trace 是在什么条件下产生的"；Score 是"这条 trace 的产出好不好"。

    2.5 低层 API：`create_score`

    所有打分最终都落到一个统一的低层方法 create_score。先看这个，后面所有写法都是它的封装：

    from langfuse import get_client

lf = get_client()

# 4 种 parent × 4 种 data_type 的组合
lf.create_score(
    name="helpfulness",        # 必须先在 UI Score Configs 里建好
    value=0.85,                 # 按 data_type 取值
    data_type="NUMERIC",        # 4 选 1

    # 4 选 1 的 parent 字段（至少填一个）：
    trace_id="01H...",          # 挂 trace
    # observation_id="...",    # 挂某个 observation（必须同时给 trace_id）
    # session_id="sess-abc",   # 挂 session（不与 trace/observation 关联）
    # dataset_run_id="...",    # 挂 dataset run（实验场景，0006 详讲）

    comment="Correct and concise",   # 可选，TEXT 类型 1-500 字符
    # config_id="...",                # 可选，关联到 Score Config
    # score_id="...",                 # 可选，幂等键
)

    代码逐行说明：

    • name：必须先在 UI Score Configs 注册，否则 CATEGORICAL 会被服务端 400 拒绝
    • value：随 data_type 走。BOOLEAN 必须 0/1，TEXT 必须 1-500 字符
    • data_type：显式声明比不写好（不写会让服务端推断；推断错版本就翻车）
    • trace_id / observation_id / session_id / dataset_run_id：4 选 1+。挂 observation 时必须同时给 trace_id（Langfuse 用它做完整性校验）
    • comment：评分理由。LLM-as-a-Judge 场景下基本必填，否则事后分不清分是怎么打出来的
    ⚠️ 坑：4 个 parent 字段同时填会怎样？服务端只认第一个非空，其他忽略。所以挂 observation 时必须只填 trace_id + observation_id，别加 session_id 进去。

    3. Evaluator 是一等公民

    3.1 v3+ 推荐模式：Evaluator + Rule

    直接 score_current_trace() 写死在业务代码里——能用，但有两个问题：

    1. 评分逻辑耦合业务代码：改了打分标准要发版
    2. 不能选择性采样：要么全打要么全不打；production 上 LLM Judge 成本吃不消

    Langfuse v3+ 的解决方式是把 Evaluator + Rule 抽到平台层。业务代码只管产生 trace，平台决定哪些 trace 给哪个 evaluator 打：

    核心收益：

    • 改打分逻辑 / 调 sampling rate → UI 改完立即生效，不用发版
    • 同一个 trace 可以挂多个 evaluator（一个评 helpfulness，一个评 tone）
    • 成本可控：sampling rate 0.1 表示只评 10% 的 trace

    3.2 Rule = filter + sampling rate

    Rule 是 Evaluator 的触发器。两条核心配置：

    配置做什么例子
    filter 选目标 observation（SQL-like 条件） isRootObservation = true AND tags contains "prod"
    sampling rate 匹配的 trace 里再抽多少比例真打 filter 命中后只评 10%（成本控制）

    两个例子，差别立现：

    # 例 1：评所有 prod 环境里 root observation 的输出
filter: isRootObservation = true AND environment = "prod"
sampling_rate: 1.0   # 100%，prod 全打

# 例 2：评 5% 的所有 trace（成本敏感型 LLM Judge）
filter: isRootObservation = true
sampling_rate: 0.05
    直觉：Rule 像水龙头——filter 是"哪些 trace 流过这里"，sampling rate 是"流过的有百分之几真接上 evaluator"。

    3.3 Observation-level 是首选（⚠️ trace-level v4 弃用）

    Evaluator 挂在哪个层级也是个非显然的选择。Langfuse v3 时可以挂 trace 级和 observation 级；v4 把 trace 级弃用了（2026-11-16 cutover）。

    层级何时评取舍
    Observation-level ✅ 推荐 每条 observation 独立跑 evaluator 更精确的 target（按 observation 类型过滤）；秒级完成；可对同 trace 不同 observation 跑不同 evaluator
    Trace-level ⚠️ v4 弃用 整条 trace 跑一个 evaluator 上下文更全（能看到多步），但 v4 不再支持。新项目一律走 observation-level

    observation-level evaluator 的 filter 经典模板：

    {
  "type": "boolean",
  "column": "isRootObservation",
  "operator": "=",
  "value": true
}

    意思是"挑出每条 trace 的根节点"——大多数 LLM-as-a-Judge 想评估的就是根节点的那次 LLM 调用（agent 决策层）。

    ⚠️ 坑：v4 self-hosted 默认就启用了 deprecation。trace-level evaluator 配了会报 warning 但仍能跑（迁移期内）；2026-11-16 之后强切。新项目直接 observation-level，不要在 lesson 演示 trace-level。

    3.4 Evaluator 的 3 种实现

    虽然 Evaluator 在 UI 上是统一概念，但它有 3 种实现方式——这一节给个总览，Part 2 逐个讲细节：

    类型用 SDK 还是 UI何时用代码约束
    Code Evaluator UI 注册（更主流）或 inline 确定性检查：JSON 合法、长度限制、关键词、exact match stdlib only / 2s 超时 / <256 KB
    LLM-as-a-Judge UI 注册（带版本） 语义判断：helpfulness、tone、correctness、是否礼貌 judge prompt 三段式；用 Evaluator 自带版本管，不用 Prompt Management
    Annotation Queue UI 操作 内部专家标注；LLM Judge 不确定的样本 人工操作，无代码
    Part 2 预告：下两节（part 2 和 part 3）会逐个讲：① 手工 SDK 调 score_current_trace（不依赖 UI）② Code Evaluator 的 UI 注册和 inline 写法 ③ LLM-as-a-Judge 的 prompt 设计 ④ Annotation Queue 工作流 ⑤ 用户反馈闭环 ⑥ UI + Analytics 查分。

    4. 一句话总结

    Score = 4 种 data_type × 4 个 parent × 3 种 Evaluator 实现。生产模式是 UI 上注册 Evaluator + Rule，业务代码只管产生 trace。
