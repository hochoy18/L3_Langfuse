    一、可观测性（Observability）

    1.1 三层结构（Trace / Observation / Session）

    1.2 4 类附加属性（Trace 级 vs Observation 级）

    以下属性附加在 Trace 上，SDK 会自动 propagate到该 trace 下的每一条 observation 行（底层是单张 observations 表的字段副本）：

    属性类型典型用途何时设
    metadata dict 环境 / user_id / feature_flags / app_version / request_id 事中（trace 创建时或过程中）
    tags list[str] 业务级维度切分（env / 业务线 / 实验组） 事先已知 + 创建时设定 + 不可变
    user_id str 终端用户标识（按用户聚合） 每条 trace
    session_id str 多轮会话聚合 同 session 下所有 trace 同值

    1.3 异步上报机制（async queue + batch flush）

    关键点：

    • SDK 是非阻塞的——app 立即返回用户响应，trace 入库在后台批量发送
    • app latency 不受影响（官方 FAQ 明确）
    • 长跑应用（web server / API）：exporter 持续运行，不需要 flush
    • 短跑脚本（一次性 ETL / batch job）：必须显式 flush()，否则进程退出前未发送的 trace 会丢失
    • 底层基于 OpenTelemetry 标准（不是 Langfuse 自有协议）

    二、Score 数据模型（4×4 矩阵）

    2.1 Score 4 个附加层

    2.2 4 种 data_type

    类型value典型场景备注
    NUMERICfloat（0-1 或 1-5）helpfulness 0.92、tone 0.7最常用
    CATEGORICAL字符串"good"/"neutral"/"bad"必须匹配 Score Config 预定义类别
    BOOLEAN0 / 1pass / fail、JSON 可解析v3 API 读出时是 bool
    TEXT1-500 字符字符串judge reasoning 一句话仅作 comment 用
    ⚠️ 常见错：同时填多个 parent 字段（trace_id + session_id）会被服务端忽略其余。挂 observation 必须只填 trace_id + observation_id。

    三、评估机制（Evaluation）

    3.1 Evaluator + Rule 触发模型

    3.2 3 种 Evaluator 实现

    类型何时用代码约束产生 Score 的 data_type
    Code Evaluator 确定性检查：JSON 合法 / 长度 / 关键词 / exact match stdlib only · 2s 超时 · <256 KB BOOLEAN / NUMERIC

    3.3 评估层级选择（v3+ 推荐 / v4 弃用警告）

    层级状态取舍
    Observation-level ✅ v4 推荐 更精确的 target（按 observation 类型过滤）；秒级完成；不同 observation 可挂不同 evaluator
    Trace-level ⚠️ v4 弃用（2026-11-16 cutover） 上下文更全但已不推荐；新项目一律 observation-level

    四、Prompt 管理

    术语定义避免的别名
    Prompt Langfuse 中一个具名、可版本化的 prompt 对象。 Template
    Prompt Version Prompt 的某一次发布。同名 prompt 多次创建即产生新版本（不覆盖）。 Revision
    Label 贴在某个版本上的可读标签（"production"、"staging"、"latest"）。SDK 默认拉 production。 Tag（与 Trace Tag 不同概念）
    Text Prompt 单字符串 + {{var}} 插值的 Prompt 类型。 String Prompt
    Chat Prompt 多 messages 列表的 Prompt 类型。 Messages Prompt
    compile 把 {{var}} 占位符替换为真实值，生成可发给 LLM 的最终字符串 / 列表。 render / format
    get_langchain_prompt 把 Langfuse Prompt 转成 LangChain 的 ChatPromptTemplate（{{var}} → {var}）。 —
    ⚠️ 关键坑：update_current_generation(prompt=...) 必须传 PromptClient 对象（p），不是 compile 后的字符串（compiled）。传字符串只会把内容塞进 input 字段，不会建立 Prompt 徽章链接。

    五、数据集与实验（Dataset & Experiment）

    术语定义避免的别名
    Dataset 离线测试用例集合（name 唯一），含 N 个 DatasetItem。 Test Set / Benchmark
    DatasetItem 一条样本：input + 可选 expected_output。同 id 写入会 upsert。 Sample / Example
    Experiment / DatasetRun 用某个应用变体（prompt / 模型）跑 Dataset 一次的过程。自动产生 trace + DatasetRunItem。 Eval Run / Benchmark Run
    DatasetRunItem 一次实验里一条样本的产出。dataset_item_id + trace_id 二者关联。 Sample Result

    六、SDK API 速查

    6.1 观测层

    API用途何时用
    @observe(name="...")装饰器包函数为 Trace / Span / Generation业务代码最简单接入
    @observe(as_type="generation")手动指定 Observation 类型想精确标记类型时
    CallbackHandler()LangChain / LangGraph 适配器ReAct / 自定义 chain
    start_as_current_observation(as_type=...)上下文管理器建 observation装饰器不够灵活时
    update_current_trace(...)给当前 trace 加 user_id / metadata 等trace 还在进行中
    update_current_generation(...)给当前 generation 加 model / usage / promptLLM 调用后立即写
    get_client().flush()强制刷写 buffer短脚本退出前必调

    6.2 评估层

    API用途
    score_current_trace(name, value, data_type)给当前 trace 打分（context 内）
    score_current_span(name, value, data_type)给当前 observation 打分（context 内）
    create_score(name, value, trace_id=, session_id=, ...)低层 API，跨 context 用
    propagate_attributes(user_id=, session_id=, tags=, metadata=)上下文管理器传递顶级属性到所有子 observation

    6.3 Prompt 层

    API用途
    create_prompt(name, type, prompt, labels, config)创建新版本（同名多次调用 → 新版本）
    get_prompt(name)取带 production label 的版本
    get_prompt(name, label="staging")取带特定 label 的版本
    get_prompt(name, version=3)取指定版本号（用于复现）
    prompt.compile(**kwargs)替换 {{var}} 占位符
    prompt.get_langchain_prompt()转 LangChain ChatPromptTemplate

    6.4 实验层

    API用途
    create_dataset(name, description)创建 dataset
    create_dataset_item(dataset_name, input, expected_output)添加 / 更新一条样本
    dataset.run_experiment(name, task, evaluators)跑实验：自动产生 trace + 挂 evaluator

    七、部署与架构（Deployment）

    组件角色v4 必要性
    Langfuse Web主应用服务（UI + API），暴露 :3000必需
    Postgres元数据 / trace / score / dataset 结构化数据必需
    ClickHousetrace 时序数据（v4 强校验连通性）v4 必需
    Redis队列 / 缓存 / 速率限制必需
    Worker异步 job（eval 队列 / score 删除 / 大 payload 上传）在线评估时必需
    MinIO / S3对象存储（多模态 / 导出快照）多模态场景必需

    events_only mode（v4 自托管默认）：SDK 走 OTEL 协议上报；旧的 /api/public/traces 等 REST 端点会被 404。要查数据用 v2/observations API 或 Langfuse CLI（npx @langfuse/cli）。

    八、我们的抽象层：TraceMetadata

    我们自己的工程化抽象——把分散的字符串 metadata 字典收敛成分类配置。基于 Pydantic BaseModel，6 大分类 + IdentityConfig + 组合类，详见 metadata-cheatsheet.html 与 Lesson 0003。

    类字段用途
    IdentityConfigsession_id / user_id / tags / trace_name（alias="langfuse_*"）4 个 langfuse_* 顶级字段
    AgentMetaagent_name / agent_version / agent_strategyagent 自身标识
    RuntimeMetaenvironment / app_version / deployment_id / request_id / input_source环境 + 请求
    ExperimentMetaexperiment_bucket / variant_id / feature_flagsA/B + 灰度
    ModelMetatemperature / max_tokens / top_p / model_nameLLM 参数
    BusinessMeta（全 custom）业务自定义字段
    TraceMetadata组合上述 6 类唯一对外暴露；含 to_langchain_config() / to_flat_dict() / from_env()
    设计要点：
    • 所有 Meta 子类用 ConfigDict(extra="allow")——允许任意自定义字段
    • IdentityConfig 用 Field(alias="langfuse_*")——调用方写 session_id=...，序列化自动加前缀
    • 类型硬约束（tags: List[str]）防止 silent failure（CallbackHandler 对非 list 的 langfuse_tags 会静默忽略）
