    REFERENCE · PROMPT STORAGE INTERNALS

    Prompt 存储内部

    Postgres 表结构 + audit_logs + is_active 真相。仅给需要深挖的 on-call / 合规审计。
    本页目标
    直接看 Langfuse v4 自托管 Postgres 里 prompt 相关表长什么样。重点：哪些是事实、哪些是设计选择、哪些是历史遗留。

    1. prompts 表（核心）

    prompts (
 id              text PK,           -- 每版独立 UUID
 created_at      timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
 updated_at      timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
 project_id      text NOT NULL,
 created_by      text NOT NULL,     -- "API" / "USER"
 name            text NOT NULL,     -- 跨版本共用的逻辑键
 version         integer NOT NULL,
 is_active       boolean NULL,      -- ⚠️ 历史遗留字段，不用
 config          json NOT NULL DEFAULT '{}',
 prompt          jsonb NOT NULL,    -- text=str / chat=messages 数组
 type            text NOT NULL DEFAULT 'text',
 tags            text[],
 labels          text[],           -- GIN 索引，高效按 label 查
 commit_message  text,

 UNIQUE (project_id, name, version)  -- 同一 project 下同名只能有一个 v1
)

    5 个有意思的 schema 细节

    观察含义
    UNIQUE (project_id, name, version)业务逻辑："同一逻辑名 v1 只能有一条"
    labels / tags 都有 GIN 索引支持高效"按 label 查询"
    prompt 是 jsonb 不是 textchat prompt 的 messages 数组就靠这个
    created_by 是 NOT NULL必须记录创建者（API 或用户）
    config 默认 '{}'::json没传 config 时默认空字典

    2. is_active 字段的真相

    DB 列是 历史遗留，API 的 isActive 是动态算出来的。

    实测对账（用我们本地的 movie-critic）

    来源v1v2
    DB 列 is_activeNULLNULL
    API isActivetruefalse
    API labels["production"]["latest"]

    推断 API 的计算规则

    isActive = "production" in labels
    labelsisActive
    ["production"]True
    ["latest"]False
    ["production", "staging"]True
    ["staging"]False
    []False
    结论：API 的 isActive 含义是"这个版本是不是 production label 当前指向的版本"，不是"是不是活跃 row"。
    ⚠️ DB 的 is_active 列是历史遗留（未使用），UI 和 API 的 isActive 才是真相。

    3. audit_logs 表（重要：审计范围有限）

    audit_logs (
 id, created_at, updated_at,
 user_id,                  -- 谁操作的
 project_id,
 resource_type text,       -- 'prompt' / 'trace' / ...
 resource_id,
 action text,              -- 当前只有 'create'
 before text,              -- 变更前完整快照
 after text,               -- 变更后完整快照
 org_id,
 user_org_role,
 user_project_role,
 api_key_id,
 type                       -- 'USER' / 'API'
)

    实测查到的 action 类型

    SELECT DISTINCT action FROM audit_logs;
-- 只有一行: 'create'

    关键缺口：label 切换不审计

    操作是否记 audit
    创建版本✅ 记（create action）
    切 production label❌ 不记
    自动 latest 转移❌ 不记
    update_prompt 改 labels❌ 不记
    ⚠️ 唯一能看出 label 改过的痕迹：prompts.updated_at + 创建时刻的 labels + commit_message。

    4. 实际查到的数据（movie-critic）

    SELECT action, before, after FROM audit_logs WHERE resource_type = 'prompt';

| action | before | after（labels 部分）                            |
|--------|--------|------------------------------------------------|
| create | NULL   | v1, labels=["production", "latest"]             |
| create | NULL   | v2, labels=["latest"]                           |

-- v1 的 'latest' 被 v2 摘走这件事完全不记 audit

    但 prompts 表里有物理痕迹：

    v1.created_at = 2026-09-16 05:32:17   ← v1 创建
v1.updated_at = 2026-09-16 05:46:07   ← 被 v2 创建连带改了 labels
v2.created_at = 2026-09-16 05:46:07   ← v2 创建时刻
v2.updated_at = 2026-09-16 05:46:07   ← 等于 created_at（labels 没再被改）

    v1 和 v2 的时间戳精确到毫秒一致——这是 Langfuse 内部事务的物理痕迹。

    5. label 历史怎么还原

    每个版本的 created_at / updated_at / 创建时的初始 labels + commitMessage → 拼出 label 在 N 个版本间的迁移路径。

    两条间接还原途径

    途径 A：从 trace 反推

    # 查"v5 上线期间"的所有 trace
traces = lf.api.observations.get_many(
    filter='{"promptVersion": 5}',
    fromStartTime='2026-09-01',
    toStartTime='2026-09-10',
)
# 看时间分布 → 反推"v5 在哪个时间段是 production"

    途径 B：commit_message + 创建时机

    v3: "v2 had safety issue, revert to safety disclaimer"
v5: "A/B test vs v4, +12% conversion"
v7: "promote v7 to prod, monitor 24h"

    从 commit_message + created_at 也能拼出大致时间线。但只依赖人工纪律。

    6. 合规审计的实操建议

    Langfuse 当前审计范围有限，要严格合规需要外面套一层自己的 audit log：

    # prompt_audit.py —— 部署到所有改 prompt label 的入口
from datetime import datetime
import json

def promote_to_production(name: str, version: int, reason: str, ticket: str = ""):
    lf = get_client()
    audit = {
        "timestamp": datetime.utcnow().isoformat(),
        "action": "promote_to_production",
        "prompt_name": name,
        "version": version,
        "reason": reason,
        "ticket": ticket,
        "actor": os.getenv("USER", "unknown"),
    }
    with open("/var/log/prompt-audit.jsonl", "a") as f:
        f.write(json.dumps(audit) + "\n")
    lf.api.prompts.update(name=name, version=version, new_labels=["production"])

    把这种函数包成 CLI / CI 步骤，所有切 label 都走这里 → 自己的审计日志就有了。
